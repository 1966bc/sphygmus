# sphygmus — Conventions

The general rules are those of
[fundamenta](https://github.com/1966bc/fundamenta) and of its part on Python,
Tkinter and SQLite: PEP 8 at 79 columns, `.format()`, one exit per
function, composition and no mixins, `Log` written by hand, `unittest`. They
are not restated here. This file holds what belongs to this project: what it
is, what it must never do, and where it departs from those rules.

## What it is

A home blood pressure diary for **one person**. Readings are typed in from
an automatic upper-arm device; the program lists them, draws them and
prints a report to take to the doctor.

It is also meant to be read. The domain is one that anybody understands, and
the program is small enough to follow from end to end: a schema, a few
windows, a chart drawn by hand, a PDF, invented data and the tests. Every
choice below says why, because the why is the part worth learning.

It is not a medical device. It records and shows; it does not diagnose,
advise or interpret. The doctor does that.

## The rules of the domain

**R1. A reading is stored as the device showed it, and nothing derived is
stored.** Systolic, diastolic and heart rate, three integers, one row per
reading. Means, minima, maxima and flags are computed when they are shown.
A stored mean is a second copy of the readings, and two copies of the same
thing end up disagreeing.

**R2. One field for date and time**, `recorded_at`, ISO 8601 down to the
second: `2026-10-11 08:00:00`. It sorts correctly as text, SQLite's
`date()` and `time()` read it, and a period is a plain `BETWEEN`. The
screen and the report split it into date and time, and show the date the
Italian way, `11/10/2026`; the database never holds a local format. Three
readings taken one after the other are three rows a minute apart: no
session table is needed to know they belong together.

**R3. One person, no patient table.** The database *is* that person's
diary. A `patient_id` on every row would be a filter on every query, and a
query that forgot it would mix two people. The name for the report heading
is a setting.

**R4. The threshold is data, and it only flags.** 135/85 mmHg, the home
threshold of the ESH 2021 position paper on home monitoring, lives in
`settings`. A reading is flagged when systolic **or** diastolic reaches it
(`>=`, as the guidelines write their thresholds). The flag highlights a row
and draws two dashed lines on the chart; it is never stored and never
called a diagnosis. If the doctor gives another threshold, a row changes and
the code does not.

**R5. Position is master data.** `positions` holds seated and lying down.
Statistics are always grouped by it: the two are not the same measurement
and are never averaged together.

**R6. Nothing is deleted, and a reading is never changed.** Every table
carries `enable`. A reading typed wrong is disabled and typed again, with
the same date and time if need be: the unique index on `recorded_at` counts
only enabled rows. The program does both in one transaction. The database
holds the rule itself, with triggers: a `DELETE` on `readings`, or an
`UPDATE` of anything but `enable`, is refused whoever sends it, the shell
included. Two more triggers write to `audit_readings` when each reading
was typed in, disabled or enabled again.

**R7. No real reading in the repository. Ever.** Not in the sample
database, the tests, the screenshots, the commit messages or the issues.
The repository is public. Sample data is invented, generated by a script
with a fixed seed, and the diary file (`*.sl3`) is ignored by git.

## Structure

**Composition, and no mixins at all.** A class *has* its collaborators as
attributes, and inherits only where *is a* is true: `App(tk.Tk)`, a window
from `tk.Toplevel`, `Calendarium` from `ttk.LabelFrame`. Not even a one-line
helper class mixed into every window: each window reaches the engine with
one line of its own.

**The Observer where something changes under somebody else's eyes.** A saved
reading notifies `readings`; the list, the chart and the statistics are
separate parts of the main window, each subscribed, and the entry strip that
saved knows none of them. A changed threshold notifies `settings`.

`ui/calendarium.py` is derived from
[Calendarium](https://github.com/1966bc/calendarium) 2.5, rewritten as one
class because the original shares its logic through a mixin.

## Dependencies

The standard library, plus **ReportLab** for the PDF report, imported in
`try/except ImportError`: without it the program runs and the report
command says why it is unavailable.

**No plotting library.** The chart on screen is drawn on a `tk.Canvas`, the
one in the PDF with `reportlab.graphics`, both by hand: axes, scale, points
and threshold lines are a few dozen lines each, and seeing them written out
is part of the point.

## Tests

`unittest`, on a database in memory built from `sql/`. The windows are
tested too, opened for real; they need a display and skip themselves
without one, so the suite is run under a virtual screen:

    xvfb-run -a python3 -m unittest discover -s tests -v

A skipped test passes. A run without a display has said nothing about the
windows.

## Language

English in code, comments, docstrings, log messages and these documents.
The interface is Italian, written as Italian literals: there is one user and
no `_()`. Stored values such as `seduto` are data and are not translated.
